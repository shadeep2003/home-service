# Two-level service directory

Admins continue managing `service_categories`. Providers manage their own named offerings at `/provider/subcategories`, linked from both their dashboard and profile editor. Names are trimmed and compared case-insensitively within a parent category. Providers cannot move an existing offering to another parent or edit another owner's offering. Inactive parents cannot receive new or edited offerings.

Public navigation is `/services` → `/services/{category:slug}` → `/services/{category:slug}/{subcategory}`. Both levels must be active. Listings require a provider role, no suspension, and a provider profile. Search matches provider name or service area, and pagination preserves the search query. Availability and working status remain informational, as in the existing directory.

`service_subcategories` holds the parent, nullable creator, normalized name, description, and active flag. `provider_subcategories` holds the offerings. Foreign keys restrict deleting referenced subcategories and parents. Provider reviews remain attached to users. Removal is blocked if another provider offers the subcategory. Removing an owner's final offering for a selected parent creates/reuses a General offering so their profile and reviews remain discoverable. General offerings have no provider owner and cannot be edited/deleted through provider management.

The additive schema migration and separate repeatable backfill preserve the old `provider_services` pivot. For every association without an existing offering, the backfill creates/reuses `General <category>` (limited to 100 characters) and attaches the provider. This includes suspended providers and inactive categories, preserving their links for later reactivation. It never changes users, profiles, photos, reviews, passwords, verification, or suspension. Registration and profile updates use the same General fallback; custom offerings remain attached when editing profile category selections. The demo seeder uses this mechanism only when creating its own new demo providers.

Apply to the configured database with `php artisan migrate`. No seeding, user recreation, or `migrate:fresh` is required. The data migration's rollback preserves associations because it cannot distinguish backfilled associations from later edits. Rolling back the schema removes only the two new tables; original category associations and account data remain. Reapplying migrations reconstructs General offerings from the original pivot, but custom offering names removed by schema rollback cannot be recovered without a backup.

Feature coverage is in `ServiceSubcategoriesTest` and the updated provider foundation, admin suspension, and review tests. Tests use isolated SQLite; the application database is not modified by the test suite.
